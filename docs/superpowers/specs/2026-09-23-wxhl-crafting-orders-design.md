# 无限回廊 · 工坊订单系统（代工委托）设计文档

日期：2026-09-23
归属：`src/wxhl-003/crafting/order/`（工坊新增「订单」页签）+ `cloudflare/wxhl-market/worker.js` 新增独立段

## 1. 背景与目标

工坊已有配方、制作、图纸系统，但产出只能自用或挂自由市场零售。本设计增加**跨玩家悬赏式代工**：发单人提出需求并支付订金，接单者**用自己的材料与图纸**制作并交付，验收后收取尾款。

与世界书《店铺经营与商业系统》的「代工橱窗」有一处关键差异，**这是有意为之**：

| | 世界书代工橱窗 | 本设计 |
|---|---|---|
| 材料 | 客户提供 | **接单者自备** |
| 图纸 | — | **接单者自备** |
| 发单人付出 | 材料 + 加工费 | **只要出钱** |

因此世界书那条退化为 v3 店铺特权，两者可并存。另：主卡 schema 的 `契约者.个人产业.代工与订单`（`{进行中订单, 冻结资金_UP}`）**本设计不使用**——它是为世界书那套橱窗预留的。

## 2. 决策记录（已与用户确认）

| 决策点 | 结论 |
|---|---|
| 订金归属 | **接单时立即转给接单者**（接单即有收入） |
| 退货时订金 | **不退**——发单人损失订金，接单者损失材料与时间 |
| 弃单处理 | 记 0 星 + **强制赔偿（订金 × 3）**，订单取消且**不回流大厅**，通知发单人（随赔偿款通知） |
| 尾款不足 | 「完成验收」按钮禁用（交不起钱不让收）；若真发生 → 订单取消、成品退回接单者、**不计入评价** |
| 验收超时 | 48h 未操作 → 尾款足则**自动验收**，不足则自动取消退货 |
| 评价粒度 | 0–5 星，**可非整数**（平均星） |
| 评价存储 | **只存 localStorage**（与既有 API 配置同处），服务器不保存、不汇总 |
| 服务器职责 | **纯中转**：只留飞行中订单，双方领取后立即删除 |
| 界面 | 工坊新增「订单」页签，内含「订单大厅」「我的」两个子页签 |
| 手续费 | **无**（订金/尾款已结构化经济，故不叠加手续费；如需可后续加常量） |

## 3. 订单生命周期

```
① 发布   发单人填「需求单」+ 订金 + 尾款 → 支付订金 → 服务器托管
② 接单   接单者接单（原子：仅当「待接单」）→ 订金转为「待接单者领取」
③ 交付   接单者选背包里一件成品提交 → 成品移出背包、上传**服务器托管（escrow）**，等待发单人领取
④ 验收   发单人 →  满意：付尾款（不足则按钮禁用）→ 尾款转接单者 → 可选打分 0–5
                   不满意：成品**从服务器托管直接退到接单者待领** → 订单取消 → 【订金不退】
⑤ 弃单   接单者弃单 → 记 0 星 + 赔偿 订金×3（本地扣、经服务器转发给发单人）→ 订单取消
⑥ 撤销   发单人在「待接单」阶段可撤销 → 订金退回
⑦ 超时   已交付满 48h 未验收 → 尾款足则自动验收；不足则自动取消退货
```

**超时的触发方式（服务端惰性求值）**：服务器无法主动推送，故超时由**服务端在读取时判定** —— 任何一方调用 `/order/mine` 或 `/order/list` 时，服务端先扫描该用户名下 `status='已交付'` 且 `now - updated > 48h` 的行，就地推进为「自动验收」（挂尾款、无评分）或「自动取消退货」，再返回结果。客户端不自行判定超时，避免两边时钟/逻辑不一致。

**状态机**（服务端为权威）：

```
待接单 ──接单──> 已接单 ──交付──> 已交付 ──验收──> 已完成
  │                 │                │
  └─撤销─> 已取消     └─弃单─> 已弃单   └─退货/超时─> 已取消
```

**双方领取物**：

| 阶段 | 接单者领取 | 发单人领取 |
|---|---|---|
| 接单 | 订金 | — |
| 交付 | — | 成品 |
| 验收 | 尾款 | — |
| 退货 | 退回的成品 | — |
| 弃单 | — | 赔偿款（订金×3） |
| 撤销 | — | 退回的订金 |

**「领取」的统一机制（escrow 托管 + 客户端结算）**：服务器只记录"该给谁什么"，**实际入账发生在客户端**。成品走 **escrow**：交付时接单者客户端把成品移出背包并上传，**服务器把它托管在订单行的 `item_json` 里**；发单人领取时才从托管收进背包，退货时**直接从托管退到接单者的待领**——发单人的背包自始至终不参与成品中转。钱走客户端结算：订金/尾款在付款方客户端扣除，服务器只记数，收款方按待领清单领取入账。客户端每次打开工坊订单页时拉 `/order/mine`，看到待领取物就执行本地结算（加 UP / 入背包），逐条调 `/order/ack` 回执，**回执 `first=true` 才入账**（重复回执说明另一标签页已入过账，不得再发一次钱）；应领项全部置位后服务端删行。因此：

- **退回的成品**直接从服务器托管退到接单者待领，不依赖发单人配合（不存在"成品滞留发单人背包"的问题；滞留只发生在行本身，由 purge 兜底）
- **赔偿款**（v4b）由**接单者客户端**扣自己的 UP 并回报，发单人再领取
- 所有本地结算都遵循工坊既有纪律：**入口先 `syncFromMvu()`、写入基取新读值、一次 `commit`、只写 `契约者.背包` / `契约者.经济.UP`**

## 4. 服务器设计（纯中转）

### 4.1 存储纪律

- **只留飞行中订单**：双方各自领取后 `ACK`，两侧都 ACK 完 → **立即删除该行**
- **不留历史、不留评价汇总表**——历史与平均星只存在于客户端 localStorage
- 成品 JSON **卡 4096 字节**（与市场同一口径）
- 独立建表 `ensureOrderSchema`，**排在市场 `ensureSchema` 之前**（照排行榜已验证的隔离套路）；订单出问题不波及市场
- 兜底清理端点 `/order/admin/purge`（照排行榜的 admin 套路，密钥缺失一律 403）

### 4.2 表结构

```sql
CREATE TABLE IF NOT EXISTS orders (
  id          TEXT PRIMARY KEY,
  poster      TEXT NOT NULL,      -- 发单人姓名
  maker       TEXT,               -- 接单者姓名（NULL = 未接）
  spec_json   TEXT NOT NULL,      -- 需求单
  deposit     INTEGER NOT NULL,   -- 订金 UP
  final       INTEGER NOT NULL,   -- 尾款 UP
  status      TEXT NOT NULL,      -- 待接单/已接单/已交付/已完成/已取消/已弃单
  item_json   TEXT,               -- 成品（交付后）
  rating      REAL,               -- 评分 0-5（完成后）
  comp_json   TEXT,               -- 赔偿款（弃单时）
  poster_ack  INTEGER DEFAULT 0,  -- 发单人已领取
  maker_ack   INTEGER DEFAULT 0,  -- 接单者已领取
  created     INTEGER NOT NULL,
  updated     INTEGER NOT NULL
);
```

### 4.3 端点

| 端点 | 方法 | 作用 |
|---|---|---|
| `/order/create` | POST | 发布（校验订金 > 0、需求单合法） |
| `/order/list` | GET | 订单大厅（`status=待接单`） |
| `/order/accept` | POST | 接单（**原子**：`UPDATE ... WHERE id=? AND status='待接单'`，受影响 0 行则拒绝） |
| `/order/deliver` | POST | 交付（挂成品，校验体积上限） |
| `/order/confirm` | POST | 验收（挂尾款 + 评分；服务端不校验余额，余额由客户端在调用前校验） |
| `/order/reject` | POST | 退货 |
| `/order/abandon` | POST | 弃单（挂赔偿款） |
| `/order/cancel` | POST | 发单人撤销（仅「待接单」） |
| `/order/mine` | GET | 我的（作为发单人 / 接单者 + 各自待领取物） |
| `/order/ack` | POST | 领取确认（双方都 ACK → 删行） |
| `/order/admin/purge` | POST | 兜底清理（旧行） |

**身份**：与市场/排行榜一致，只按**姓名**记名，服务端不做身份校验（既有信义模型）。

### 5.2 需求单（zod，纯函数可测）

```ts
const 需求单Schema = z.object({
  名称: z.string(),                                  // 想要的成品名/方向
  成品类型: z.enum(['装备', '道具']),
  装备子类: z.enum(['武器', '防具', '饰品']).or(z.literal('')).prefault(''),
  品质: z.enum(['金色', '紫色']).or(z.literal('')).prefault(''),  // 空 = 不限
  阶位: z.coerce.number().prefault(0),               // 0 = 不限
  效果要求: z.string().prefault(''),                  // 自由文本
  说明: z.string().prefault(''),                      // 自由文本
});
```

**数量恒为 1**（一单一物，简化赔付与验收；如需多件再立）。

### 5.3 评价与订单记录（localStorage）

- 存储键：`wxhl003_order_rep`（与既有 `Settings` 同样走 `localStorage`）
- 结构：

```ts
interface 评价库 {
  记录: { 订单id, 角色: '发单人'|'接单者', 对方: string, 需求单, 评分?: number, 结果: string, 时间: number }[];
  汇总: Record<string, { 次数: number; 总分: number; 平均: number }>;  // 键 = 对方姓名
}
```

- **平均星本地算**：`平均 = 总分 / 次数`（保留一位小数）
- 弃单自动记 **0 星**；付不起尾款取消的**不计入**
- 展示：订单大厅里每张订单旁显示发单人的历史平均星；「我的」里显示自己的平均星 + 「顾客评价和订单记录」列表

### 5.4 UI

**订单页签**（工坊第 4 个页签：配方 / 制作 / 材料 / 订单），内含两个子页签：

**订单大厅**
- 顶部：「发布订单」表单（需求单字段 + 订金 / 尾款 + 合计提示）
- 列表：所有「待接单」订单（需求单摘要 + 发单人姓名 + 其历史平均星 + 订金/尾款 + 发布时间）
- 每张卡：「接单」按钮

**我的**
- **我发布的**：状态 + 需求单 + 接单者 + 【验收/退货】按钮（已交付时）+ 评分输入
- **我接的**：状态 + 需求单 + 发单人 + 【交付/弃单】按钮
- **待领取**：待领订金 / 待领尾款 / 待领退回成品 / 待领赔偿款（各自一个「领取」按钮）
- **我的评价**：平均星 + 「顾客评价和订单记录」

## 6. 错误与边界

| 情况 | 处理 |
|---|---|
| 接单竞态（两人同抢） | 服务端原子 UPDATE，受影响 0 行即"手慢了" |
| 交付体积超限 | 客户端先校验（≤4096 字节），服务端二次校验 |
| 成品不满足需求单 | **不做机器校验**——由发单人肉眼验收（AI 不参与，用户明确要人工判断） |
| 发单人付不起尾款 | 验收按钮禁用；真发生则取消退货、不计评价 |
| 接单者领了订金后弃单 | 强制赔偿订金×3；**服务端碰不到存档，靠接单者客户端本地扣**（信义模型，非硬约束） |
| 双方长期不上线 | 管理端点 purge 兜底清理 |

## 7. 测试策略

- **Worker**：`worker.test.js` 加订单段；复用 `fake-d1.mjs`（**认不出的 WHERE 一律抛错**——这条是排行榜踩坑后的既有防线）
- **纯函数**：`spec.ts`（需求单校验）、`reputation.ts`（平均星、弃单记 0、付不起尾款不计入）走 vitest
- **冒烟**：`smoke.mjs` 加订单全流程（发布→接单→交付→验收→ACK→行删除）
- **端到端行删除**：断言双方 ACK 后 `orders` 表无该行 —— 这是"服务器不撑爆"的核心保证
- **`.vue` 无自动类型门**：派单时用既有的四道机械门（`@vue/compiler-sfc` 查 0 未解析 `_ctx`、死声明扫描、eslint、store 成员差集）

## 8. 分期

- **v4a 核心闭环**：Worker 段 + 发布/大厅/接单/交付/验收/退货 + 待领取 + ACK 删除
- **v4b 信誉与记录**：评分、平均星、订单记录、弃单赔偿
- **v4c 兜底**：撤销、超时自动验收、admin purge

**建议按 v4a → v4b → v4c 顺序做**，每期都能独立跑通并验证。
