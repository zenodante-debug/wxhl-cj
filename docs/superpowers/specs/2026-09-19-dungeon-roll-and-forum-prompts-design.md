# 副本生成模块 + 论坛提示词整改 — 设计规格

日期：2026-09-19
状态：阶段 A 已实现并通过整分支终审（2026-09-19）；用户在酒馆的实测验收进行中；阶段 B 待启动
目标产物：`dist/wxhl-003/index.js`（构建后手动导入酒馆替换同名脚本）

---

## 概述

本规格包含两个阶段：

- **阶段 A · 副本生成模块**：在小手机（wxhl-003）内新增第 5 个 App「🎲 副本生成」。玩家在手机里掷骰 → AI 按《副本生成》规则产出副本 → 写入 MVU 变量（`当前副本元数据` / `当前副本任务` / 名单）→ 组装一段「进入副本」的玩家视角提示词填入酒馆输入框（**只填入不发送**）。
- **阶段 B · 论坛提示词整改**：拆开现在被 5 个分区共用的 `WORLD_SUMMARY`，按分区注入不同参考；只有「副本经历分享区」读完整的副本生成规则；重做 5 个分区的提示词，解决「帖型千篇一律」问题。

两阶段有真实依赖（B 需要 A 先把规则常量拆开），故 A 先做、B 紧跟，写在同一份 spec 里。

### 非目标

- **不在本规格内生成敌人**。敌人生成规则复杂，待用户后续提供后作为阶段 C 单独设计。阶段 A 在卡片上预留「敌人生成」按钮与 `dungeonGen.ts` 的接缝函数。
- 不改动 `useDungeonStore`（副本攻略）的任何行为。
- 不改动 `赛季信息.当前副本周期`（进本/结算是 GM 的事）。
- 不改动 `契约者.当前世界`（本模块只生成副本，玩家尚未进本）。

`src/wxhl-003/data.ts:634` 定义了 `DUNGEON_GENERATION_RULES`，但**全项目没有任何文件 import 它**。且它是旧版，与用户现行规则不符：

| 日常副本调和规则 | 无 | **有整节（§6）** |
| 契约者匹配 IP 角色 | 按标签 `1d40` | 按标签 `1d50` |
| ★★★★★ 奖励 | 含「专属称号」 | 无 |
| ★★★★★★ 品质/类型骰 | `1d5[1-4紫 5银]`、`1d7` | `1d5[1-3紫 4-5银]`、`1d7` |

### 2. 玩家变量结构（本模块的写入目标）

来源：`mvu存档_无限回廊7.0.2`，与用户提供的 `schema.ts` 一致。

| 用途 | 路径 | 结构 |
|------|------|------|
| 新手副本判定 | `契约者.赛季信息.当前副本周期` | number，clamp 1~10，**`=== 1` 即新手副本** |
| 玩家面板 | `契约者.头部` | 姓名 / 等级 / 阶位 / 军衔 / CR / 回廊态度 / 天赋 / 血统 / 称号 |
| 战力 | `契约者.属性` / `衍生属性` / `职业` / `通用技能` / `装备` | — |

| **副本元数据** | `契约者.当前副本元数据` | `{副本名称, 副本来源, 副本类型(和平/阵营/血腥/未生成), 时间限制, 基准等级}` |
| **副本任务** | `契约者.当前副本任务` | 见下 |

| **固有角色名单** | `契约者.固有角色名单` | record(角色名 → `{位阶, 等级, 状态}`) |
| 敌人（阶段 C） | `契约者.副本角色` | record(角色名 → 实体) |

`当前副本任务` 各子结构：

```
主线任务: {名称, 说明, 奖励, 状态: 进行中/已完成/失败}
支线任务: record(任务名 → {说明, 奖励, 状态})
世界事件: record(事件名 → {说明, 奖励, 状态: 进行中/已结束})     ← 无「影响」字段
隐藏任务: record(任务名 → {说明, 奖励, 状态: 未触发/进行中/已完成})
副本成就: record(成就名 → {说明, 难度, 奖励, 状态: 未达成/已达成})
```

### 3. 现有「副本攻略」不是本模块

`useDungeonStore`（`store.ts:1270`）的职责是**给一个已存在的副本写通关路线**（读 `stat_data` 里的副本数据 → 出路线 → 存 localStorage）。本模块的职责是**掷出并生成副本本体并写进存档**。两者互不干扰，共用桌面但不同 App。

### 4. 输入框写入方式

- `slash_command.txt:227` 有 `/setinput (string)` — 将用户输入设置为指定文本。
- 回退方案：jQuery 操作 `#send_textarea` 并触发 `input` 事件（脚本的 `$` 即 `window.parent.$`，直接作用于酒馆页面）。
- **实现时必须用 chrome-devtools MCP 在实际酒馆页面验证一次**，手机端酒馆的选择器可能不同。

### 5. 项目无测试框架

`package.json` 无 `test` 脚本，仓库内无测试文件。验证方式见「验证方式」一节。

### A2. 掷骰引擎（新文件 `src/wxhl-003/dice.ts`）

**随机源**：`crypto.getRandomValues` + 拒绝采样，消除取模偏差。

```ts
function rollDie(faces: number): number   // 1..faces，crypto 随机
```

**为什么不需要骰池**：AI 无法生成真随机数，所以旧方案预埋骰池让 AI「按顺序取用」。本模块把掷骰交给 JS，**一次掷完全部骰子并锁定成数据**，AI 只做「把骰值翻译成内容」。这比骰池更硬：AI 连「取第几个」的余地都没有，且数值根本不由 AI 产出（见 A5）。

**骰子清单**（一次 `rollDungeon()` 全部掷出）：

| 阶段 | 骰子 | 说明 |
|------|------|------|
| 副本类型 | **新手副本不投骰**（强制和平）；否则 `1d4` | 1=和平，2=阵营，3~4=血腥 |
| 媒介来源 | `1d6` | 实体小说/影视作品/电子游戏/动漫作品/民俗怪谈/桌面与规则体系 |
| 题材大类 | `1d6` | 奇幻神话/玄幻仙侠/科幻未来/历史演义/现代异能/现实日常 |
| 时代背景 | `1d6` | 上古太古/古代中世纪/近代工业化/现代当代/近未来赛博/遥远未来星际 |

### A3. 契约者匹配规则

| 玩家 CR | 匹配来源 |
|------|------|
| `CR ≤ 4` | 同阶契约者，**AI 自由生成，不上榜** |
| `4 < CR < 6` | 同阶排行榜（`RANK_BOARDS` 对应榜） |
| `6 ≤ CR < 7` | 高一阶排行榜 |
| `7 ≤ CR < 10` | 高两阶排行榜（越界封顶天榜） |
| `CR = 10` | 天榜（五阶） |

门槛为 `≥6 升一阶`、`≥7 升两阶`、`=10 封顶天榜`。即：CR = 6 取高一阶，CR = 7 / 8 / 9 均取高两阶。

榜单映射（`data.ts:191` 的静态 `RANK_BOARDS`，共 5 榜 × 10 条，每榜 10 个称号）：

| 阶位 | 榜单 |
|------|------|
| 一阶 | 人榜 |
| 二阶 | 黄榜 |
| 三阶 | 玄榜 |
| 四阶 | 地榜 |
| 五阶 | 天榜 |

注意 `RANK_BOARDS` 只提供 **称号**（如「无距之刃」）与等级、势力，**没有真名**。而规则要求「真名公开，禁止代号」且格式为 `[称号]真名 Lv.X`，故**真名由 AI 补全**；CR ≤ 4 时连称号也由 AI 生成。

阶位字符串存在两套写法（schema 用「一阶」，`TIER_ORDER` 用「1阶」），`App.vue:698` 已有 `CN_TIER` 转换。**本模块复用同一套转换，不新增。**

### A4. 生成 prompt（新文件 `src/wxhl-003/dungeonGen.ts`）

`buildDungeonPrompt(roll, playerData, worldbookText)` 按序拼装：

1. **`DUNGEON_GENERATION_RULES`**（更新到 D50 新版后的全文）
2. **【已锁定骰值表】** — 本节核心。以表格列出全部骰值与映射文字，前置死命令：**「以下骰值由系统掷定且已锁定，严禁改动、重掷、忽略或自行编造任何数值」**
3. **【玩家数据】** — 从 `stat_data` 摘取：`头部`（姓名/等级/阶位/军衔/CR/回廊态度/天赋/血统/称号）、`职业`、`属性`、`小队`、`副本经历`
4. **【匹配候选池】** — 按 A3 规则取对应榜单的 10 条喂入；CR ≤ 4 时改为指令「自由生成同阶契约者，不上榜」
5. **【输出要求】** — 只回 JSON，字段与 MVU 变量一一对应

若核心特色标签 ∈ 41~50，额外注入规则 §6 日常副本调和规则的**强制执行提示**（副本类型强制视为和平、副模块降维、不生成战斗敌人、对手属性锚定 Lv.1~5 / 属性值 2~10）。

### A5. AI 输出 JSON 与「数值不可污染」设计

**关键设计**：AI **不产出任何数值**，只产出文案与物品名；所有 `UP / EXP / RP / 品质 / 类型` 的文本由模块用锁定骰值拼装。AI 因此**在结构上无法篡改数值**。

AI 返回的 JSON（`×N` 表示数组必须恰有 N 个元素，顺序即展示顺序）：

```json
{
  "副本名称": "…",
  "副本来源": "《作品名》（媒介来源）",
  "副本背景": "…",
  "时间限制": "…",
  "日常调和说明": "…（仅日常副本时非空，说明畸变方式）",
  "主线任务": { "名称": "…", "说明": "…" },
  "支线任务": [ { "名称": "…", "说明": "…", "物品名": "…" } ],
  "世界事件": [ { "名称": "…", "说明": "…", "影响": "…" } ],
  "隐藏任务": [ { "名称": "…", "说明": "…", "物品名": "…" } ],
  "副本成就": [ { "名称": "…", "说明": "…", "难度": "…", "物品名": "…" } ],
  "固有角色": [ { "名称": "…", "位阶": "…", "等级": 0 } ],
  "其他契约者": [ { "真名": "…", "称号": "…", "等级": 0, "阵营": "…" } ]
}
```

各数组的长度约束：`支线任务 ×3`、`世界事件 ×2`、`隐藏任务 ×2`、`副本成就 ×6`（严格按 ★→★★★★★★ 顺序）。

模块拼装的奖励文本格式：

```
342 UP + 187 EXP + 【蓝色】消耗品：圣水
```

（`【品质】类型：物品名`，品质与类型取自已锁定骰值的映射文字，物品名取自 AI。）

**响应校验**：用 `zod` 定义 `DungeonGenResultSchema`，`parse` 失败即报错并允许重试。数组长度必须严格为 3 / 2 / 2 / 6，成就必须按 ★→★★★★★★ 顺序（正则匹配与状态栏展示都依赖这个顺序）。

### A6. 变量写入

生成后写存档**由用户手动点「写入存档」触发**（不满意可以重 roll，不污染存档）。写入方式复用竞技场套路（`store.ts:1616-1619`）：

```ts
await waitGlobalInitialized('Mvu')
const mvu = Mvu.getMvuData({ type: 'message', message_id })   // message_id 探测逻辑复用现有模式
_.set(mvu, ['stat_data','契约者','当前副本元数据'], {...})
// …逐条 _.set…
await Mvu.replaceMvuData(mvu, { type: 'message', message_id })
```

用 `_.set` 的**数组路径**逐条写，不清空、不覆盖无关字段。

| 变量路径 | 写入内容 |
|------|------|
| `契约者.当前副本元数据` | `{副本名称, 副本来源, 副本类型, 时间限制, 基准等级: 玩家当前等级}` |
| `契约者.当前副本任务.主线任务` | `{名称, 说明, 奖励: 模块拼装, 状态: '进行中'}` |
| `契约者.当前副本任务.支线任务` | record：`任务名 → {说明, 奖励: 模块拼装, 状态:'进行中'}` ×3 |
| `契约者.当前副本任务.世界事件` | record：`事件名 → {说明, 奖励: ← 字段放 AI 的「影响」文本, 状态:'进行中'}` ×2 |
| `契约者.当前副本任务.隐藏任务` | record：`任务名 → {说明, 奖励: 模块拼装, 状态:'未触发'}` ×2 |
| `契约者.当前副本任务.副本成就` | record：`成就名 → {说明, 难度: '★★★★★ 传说级 · <难度描述>', 奖励: 模块拼装, 状态:'未达成'}` ×6 |
| `契约者.固有角色名单` | record：`角色名 → {位阶, 等级, 状态:'存活'}` |
| `契约者.其他契约者名单` | record：`真名 → {称号: '无' 时写「无称号」, 等级, 阵营, 状态:'存活'}` |

**已知映射妥协**：`世界事件` 在变量里只有 `奖励` 字段，而规则里世界事件给的是「影响」，无奖励。故把影响文本写入 `奖励` 字段。已在用户侧确认接受。

### A7. 进入副本提示词（填入输入框）

**填入的不是面板文本**，而是玩家视角的进本指令：

```
传送完成，我踏入了本次副本的降临点。本次副本的资料已经写入我的契约者档案
（当前副本元数据 / 当前副本任务 / 其他契约者名单 / 固有角色名单）。请读取这些变量，
以我进入副本后的开场场景作为回复：降临的具体地点与处境、时间限制与当前阶段、
主线任务的下达、同时降临的其他契约者、以及出现在我视野内的固有角色。
```

写入方式：优先 `triggerSlash('/setinput ' + text)`；失败则回退 jQuery `$('#send_textarea').val(text).trigger('input')`。

因该文本以**玩家消息**身份发出，措辞统一为第一人称玩家视角（与 `buildBattleIntroMessage` 同一思路，`workshop.ts:50`）。

### A8. 面板文本（仅存档/复制用）

仍按规则模板组装完整 `<Panel Enhancement>` 文本（副本任务 / 世界事件和成就列表 / 副本人物生成 三块），用于存档、回看与复制。**不填入输入框**，保持变量驱动的主流程干净。

## 阶段 B · 论坛提示词整改

### B1. 问题

`buildRefreshPrompt`（`store.ts:329-352`）给 5 个分区拼了**同一句** `WORLD_SUMMARY`，而那是一长串副本模块词表。后果：

- 交易区在生成卖装备的帖子，却被告知了 50 个副本标签 —— 无关上下文浪费 token 且分散注意力。
- 5 个分区的提示词是同一个模板句（「你是XX区的XX员，生成8条帖子」），只换了名词。
- 用户在实测中发现「只有副本经历该读副本生成提示词，其他分区不需要」。

### B2. 常量拆分（`data.ts`）

| 常量 | 内容 | 注入范围 |
|------|------|------|
| `CORE_WORLD` | 回廊机制：契约者/等级/阶位/军衔/CR 评价与回廊态度/UP·EXP·RP/职业系统/天赋血统称号/装备品质(白蓝紫金)/技能卷轴/九方势力 | **全部 5 个分区** |
| `MODULE_TABLES` | 副本词表：D4 类型 / D6 媒介·题材·时代 / D50 特色标签 / D50 副模块 / D40 IP 热度 / CR 难度修正 | 吐槽区、副本经历区、副本生成模块 |
| `DUNGEON_GENERATION_RULES` | 生成程序：抽取流程 / 冲突调和 / 三种世界逻辑 / 匹配机制 / 奖励规范 | **只有副本经历区**、副本生成模块 |
| `REWARD_RULES` | 奖励规范与梯度表 | 只有副本生成模块 |

`WORLD_SUMMARY` 保留为兼容常量或删除（实现时确认无其他引用后删除）。

### B3. 分区设计：体裁 vs 人格

**这是本节的核心修正。** 原设计的错误是给每个分区规定**一种帖型基调**（如「吐槽区 = 破防骂街」），结果 8 条帖子会是同一个人写的，千篇一律。正确模型是两层：

- **体裁层（分区决定）**：这个版块收什么类型的帖子。分区之间在此层区分。
- **人格层（每帖决定）**：8 条帖子来自 **8 个不同的契约者**，各自有不同的性格、情绪、阶位、势力、处境。**分区提示词必须显式要求人格多样性，并给出示例人格矩阵**（暴躁老哥 / 阴阳怪气 / 哭诉求救 / 装逼炫技 / 理性数据党 / 萌新小白 / 老油条 / 乐子人 / 沉默寡言 / 话痨……），要求 8 条覆盖不同阶位与势力，严禁所有帖子同一种语气。

| 分区 | 体裁层（版块文化） | 专属参考 |
|------|------|------|
| 💬 吐槽区 | 情绪宣泄为主，**强烈主观情绪**，短句、标题党、破防感。与副本经历区的区别：这里**不发故事**，发的是情绪与观点 | `MODULE_TABLES` + `CORE_WORLD` |
| 🔍 情报区 | 分析帖，讲数据、讲结论、讲规律；热评以质疑与补充为主 | `CORE_WORLD` + 势力 + CR 难度修正 |
| ⚔️ 副本经历区 | **讲故事**：有时间线、有细节、有过程、有余悸；楼层以追问「然后呢」为主 | `MODULE_TABLES` + **`DUNGEON_GENERATION_RULES` 全文** |
| 📐 构筑区 | 配装流派贴，讲属性分配/职业技能/装备搭配/实战数据；流派之间互相拆台 | `CORE_WORLD` + 职业系统 + 属性/衍生属性 + 装备槽 |
| 💰 交易区 | 买卖帖，讲价格、讲品质、讲来源；评论以砍价竞价为主 | `CORE_WORLD` + 物品品质阶位 + UP 经济 + 背包 |

### B4. 贴吧风格约束（写成可执行条款，不空喊「要像贴吧」）

每个分区提示词中加入：

- 标题形态：带 `【】` 前缀、或疑问句、或"如何评价…""在线等挺急的""家人们谁懂啊"式口语标题
- 楼主自称：楼主 / 萌新 / 老东西 / 兄弟 / 各位大佬
- 热评形态：抖机灵、抬杠、玩梗、前排、顶、+1、复读
- 允许网络口语与错别字（但**不出现具体现实平台名**，保持回廊世界观内自洽）
- **严禁 AI 腔**：禁止「作为一名契约者，我认为…」这类书面总结腔
- 楼层文化：楼主 / 层主 / 沙发 / 板凳

### B5. `generateThreadDetail` 与 `generateReplies` 同步整改

现在这两个函数（`store.ts:377`、`store.ts:401`）完全没有分区意识 —— 只拿到标题和预览。整改为按 `thread.section` 注入该分区的体裁约束与专属参考，并保持帖子原有作者的人格一致（详情页的楼主语气必须与列表页的 `author` 设定吻合，回复者复用帖子中已出现的昵称）。

## 错误处理

| 场景 | 处理 |
|------|------|
| API 未配置 | 复用现有文案「请先在终端设置中配置 API」，不发请求 |
| `generateRaw` 返回非法 JSON | 复用 `aiGenerate` 的 3 次重试与递增警告（`store.ts:114`） |
| JSON 结构不符（数组长度/顺序错） | `zod` parse 失败 → 报错 + 允许重试，不写存档 |
| `Mvu` 未初始化 | `waitGlobalInitialized('Mvu')` 等待；超时则 `toastr.error` 并保留卡片 |
| `replaceMvuData` 失败 | `toastr.error` 透出真实错误；卡片状态保持「未写入」，可重试 |
| `/setinput` 失败 | 回退 jQuery 写 `#send_textarea`；再失败则 `toastr.error` + 提供「复制提示词」按钮 |
| 未找到玩家数据 | 提示「未找到角色数据」，仍可掷骰但生成质量下降（prompt 标注数据缺失） |

## 验证方式

项目无测试框架，采用「构建 + 酒馆实测」：

1. `pnpm build` 通过（TypeScript 编译 + webpack 打包无错）。
2. `dice.ts` 的纯函数可用一次性 `node` 脚本抽查：分布均匀性（各面出现次数）、区间映射正确性（品质/类型骰 → 文字）。
3. **酒馆实测**（用 chrome-devtools MCP 连实际酒馆页面，`mcp.mdc` 要求）：
   - 掷骰面板显示的骰值与 `RollResult` 一致
   - 「写入存档」后读 `getVariables` 确认 8 条路径全部写入且数值 = 锁定骰值
   - 「填入输入框」后确认 `#send_textarea` 内容正确（**手机端视口下也测一次**）
   - 论坛 5 个分区各刷一次，人工确认**分区之间体裁不同、分区内 8 条帖子人格各异**
   - 重 roll 后再次写入，确认覆盖正确且未污染无关字段
