# 副本结算模块 · 设计

> 2026-09-20 与用户多轮对话确定。规则原文见本文件附录 A（用户提供，逐字）。
> 本设计**只覆盖到「写存档」为止**，不含结算后流程。

## 一、目标

在小手机（wxhl-003）**主页面**新增「副本结算」模块。玩家点一下 → 模块读变量快照与聊天记录 →
AI 做判定与文案 → **模块做全部算术** → 拼出 `<Settlement Beautification>` 结算画面 →
玩家确认后才写存档（**不可逆写入前置确认**）。

## 二、已确认的决定（用户逐条拍板，不要再问）

| # | 决定 |
|---|---|
| 1 | **模块算、AI 判定与写文案。** AI 只回判定与内容，**不碰任何算术结果** |
| 2 | **先出结算画面，确认后才写存档**。可「重算」 |
| 3 | **结算后流程不做进模块** —— 画面末尾列出「休息周期 / 花 UP 延长滞留」两个选项，由聊天里的 AI 接手 |
| 4 | **模块只算 EXP / UP / RP / PEXP 四个增量**，不做逐级升级、不做军衔晋升、不做职业升级阈值 —— **前端脚本自动执行升级** |
| 5 | **队友的位阶修正统一用玩家的**，且队友拿到与玩家**完全相同**的最终 EXP / UP 数额 |
| 6 | **队友的 UP 写进该成员的 `背包`**，条目名「现金UP」，数量为 UP 数额（`实体Schema` 无 `经济` 字段） |
| 7 | **RP 的区间值由模块掷骰**（不是 AI 定） |
| 8 | **成就的 RP 直接等于星数**（★=1 … ★★★★★★=6），不掷骰 |
| 9 | **副本周期 10 + 1 = 1**（不是卡在 10） |
| 10 | **称号交给聊天**：模块**不写** `称号.当前称号`，把新称号写进 `称号.备用称号（只记录不生效）` |
| 11 | **清空范围**：`其他契约者`、`副本角色`、`其他契约者名单`、`固有角色名单` 清空；`当前副本元数据`、`当前副本任务` 清零回默认 |
| 12 | **副本内天数按 `当前时间.客观时间`**（该字段记录「本次副本已度过几天」），由 AI 读出并报告。**2026-09-20 用户更正**：早先定的是 `副本日期`，是错的 |

## 三、架构与数据流

```
[点「副本结算」]
  读变量快照 + 最近聊天记录
  → buildSettlementPrompt(快照, 聊天, 世界书)
  → aiGenerate(cfg, prompt, { name:'dungeon_settlement', value: z.toJSONSchema(SettlementGenResultSchema, {io:'input'}) })
  → SettlementGenResultSchema.parse(extractJSON(raw))     ← 只含判定与文案
  → computeSettlement(ai结果, 快照)                        ← 全部算术, 纯函数
  → assembleSettlementPanel(computed, ai结果)              ← 拼 <Settlement Beautification>
  → 展示; 可「重算」
[点「确认结算」]
  → buildSettlementWrites(computed) 得到 { 路径: 值 } 的清单
  → _.set 逐条 → Mvu.replaceMvuData → 回读校验
  → 如实 toastr（成功/未生效/条目已变，与敌人生成同款）
```

**为什么面板由模块拼**：规则里的格式是固定的 `## 字段` 列表。模块拼才能保证**画面上的数字与写进存档的数字必然一致** —— 不会出现「画面写 +50 RP、存档写 +30」。这也是把面板从 AI 手里拿走的唯一理由。

**新增文件**
- `src/wxhl-003/settlementRules.ts` —— zod schema + **全部算术** + 面板拼装（纯函数，零酒馆依赖，可单测）
- `src/wxhl-003/settlementGen.ts` —— prompt 构造（纯函数）
- `src/wxhl-003/__tests__/settlementRules.test.ts` / `settlementGen.test.ts`
- `store.ts` 新增 `useSettlementStore`；`App.vue` 新增主页面图标 + `currentView: 'settlement'` 视图

## 四、AI 回的 JSON（`SettlementGenResultSchema`）

**只含判定与文案，一个算术结果都不许有。**

```jsonc
{
  "评价等级": "S",              // 'S'|'A'|'B'|'C'|'D'（F 不进结算）
  "评价依据": "字符串",          // 第一步的判定理由，明文展示
  "击杀": { "精英": 0, "BOSS": 0, "隐藏BOSS": 0 },
  "濒死次数": 0,
  "副本天数": 0,                // 从 当前时间.副本日期 与聊天记录读出
  "完成的支线": ["任务名"],      // 键名, 必须与变量里的键逐字一致
  "完成的隐藏任务": ["任务名"],
  "达成的成就": ["成就名"],
  "职业专属支线条数": 0,         // 第六步的 n
  "天赋试炼次数": 0,             // 第五步 RP 来源之一
  "掉落物品": [ { "名称": "", "品质": "", "属性": "", "效果": "", "数量": 1 } ],
  "称号": { "名称": "", "效果": {} },   // 非 A/S 级时为 null
  "史诗记录": "一句话中二诗意总结"
}
```

**「完成的支线 / 隐藏 / 成就」以 AI 报告为准**，不读变量里的 `状态` 字段。
理由：任务是否真的完成需要读聊天记录（GM 可能没同步状态）；而**奖励数值本身仍从变量里的 `奖励` 文本解析**（用户原话：「任务、奖励什么的都是在变量结构里写好了的」）。两者分工明确：**数值来自变量，完成与否来自 AI。**

### ⚠️ 必须在 prompt 里写【优先级声明】

规则原文里带着 **`<Settlement Beautification>` 这一整套输出格式**。它会被内联进 prompt，
AI 极可能**在 JSON 后面追一份结算面板**，导致 `extractJSON` 解析失败、整次结算白跑。

这与之前 `<Panel Enhancement>`（副本生成）和 `<enemy>`（敌人生成）踩的是**同一个坑**，
两处都靠在 prompt 里加【优先级声明】解决。本次必须同样处理：

```
【优先级声明】上文规则原文的「结算格式：必须被 <Settlement Beautification> 包含」那一整节
是给跑团 GM 用的, **不适用于本次生成** —— 结算画面由系统在收到你的 JSON 后另行拼装。
本次生成只按下面的 JSON 要求输出, 两处要求冲突时以本节为准。
**严禁**在 JSON 前后输出任何 <Settlement Beautification> 面板或结算画面。
```

### 另外两处需要 AI 判定、规则未定义的来源

- **「击杀稀有/隐藏BOSS 2~4」**：规则写的是「稀有/隐藏BOSS」。本设计取 `击杀.隐藏BOSS`，
  由 AI 判定本次是否击杀了隐藏BOSS（`副本角色` 容器里类型带「隐藏BOSS」的实体）。
  **若「稀有BOSS」另有所指，请指出。**
- **「天赋试炼 1~2」**：规则未说明天赋试炼是什么、由什么触发。本设计让 AI 报告
  `天赋试炼次数`（它读聊天记录判定），模块按次掷 1~2。**若它其实是某个固定机制，请指出。**

## 五、算术细则（`computeSettlement`，全部纯函数）

### 5.1 奖励文本解析

变量里的 `奖励` 是文本，格式由 `dice.ts:composeRewardText` 固定生成：

```
"50 UP + 100 EXP + 3 RP + 【金色】武器：某物"
```

模块用正则解析出 `UP` / `EXP` / `RP` 三个数。

**⚠️ 解析失败必须明确报错，绝不静默当 0** —— 报出是哪一条任务的 `奖励` 格式不对。
这是本模块唯一依赖文本格式的地方，是设计上的已知脆弱点（见第九节）。

**计入汇总的**：`主线任务`、AI 报告已完成的 `支线任务` / `隐藏任务` / `副本成就`。
**不计入**：`世界事件`（它的 `奖励` 字段存的是「影响」文本，不是数值 —— 规则第三步的 EXP 汇总也没提它）。

### 5.2 资格分（第二步）

```
资格分 = 评价分 + 击杀分 + 任务分
评价分: S+50 / A+35 / B+20 / C+10 / D+0
击杀分: 精英+5/只, BOSS+15/只, 隐藏BOSS+30/只
任务分: 支线+5/条, 隐藏+20, 成就+10/条
```

### 5.3 最终 EXP / UP（第三、四步）

```
基础EXP汇总 = Σ(各来源奖励里的 EXP)
基础UP汇总  = Σ(各来源奖励里的 UP)
最终EXP = 基础EXP汇总 × 评价倍率 × CR奖励倍率 × 位阶修正
最终UP  = 基础UP汇总  × 评价倍率 × CR奖励倍率 × 位阶修正
```

- 评价倍率：`S×2.0 / A×1.5 / B×1.2 / C×1.0 / D×0.7`
- 位阶修正：**玩家的阶数**（一阶1 / 二阶2 / 三阶3 / 四阶4 / 五阶5）—— 注意这与敌人生成的「位阶修正值系数 1/2/4/7/11」**不是同一个东西**
- CR奖励倍率：按**结算前**的 `头部.CR` 查表

**⚠️ 待确认（CR 分档的取整方式）**：规则给的区间是 `1.0~2.0漠视 / 3.0~4.0观察 / 5.0~6.0关注 / 7.0~8.0重视 / 9.0~9.9期待 / 10.0炼狱`，但 CR 是小数（结算会 ±0.5/±0.3），**2.5 这类值没有定义**。本设计取 `Math.floor(CR)` 后查表（2.5→2→漠视，9.9→9→期待，10→炼狱）。**请审这一条。**

### 5.4 RP（第五步）

```
RP = Σ 隐藏任务(每个已完成掷 1~3)
   + Σ 已达成成就的星数          ← 直接等于星数, 不掷
   + S级额外 +3
   + Σ 隐藏BOSS击杀(每个掷 2~4)
   + Σ 天赋试炼(每次掷 1~2)
   + 炼狱通关附加(CR=10 时掷 1~3, 否则 0)
```

星数从 `副本成就.<名>.难度` 的开头数 `★`（格式固定为 `'★ 探索级 · <AI难度描述>'`，由 `dungeonRules.ts` 生成）。

掷骰复用 `dice.ts` 的 `rollDie`（`crypto.getRandomValues` + 拒绝采样，无偏）。

### 5.5 PEXP（第六步）

```
单条职业专属支线 PEXP = 掷 50~100
最终PEXP = (100 + Σ单条) × 评价倍率
```

### 5.6 CR 变动（第十步）

```
S +0.5 | A +0.3 | B/C 不变 | D -0.5
```

**⚠️ 待确认（上限回调）**：规则写「CR上限10，已达10则回调至3」。本设计读作
`newCR = CR + delta; if (newCR >= 10) newCR = 3;` 最后 clamp 1~10。
**请审这一条** —— 另一种读法是「结算前 CR 已是 10 时，结算后变 3」。

`回廊态度` 按**更新后**的 CR 查同一张表（5.3 的 floor 规则）。

### 5.7 时间（第十一步）

`当前时间.现实日期`（格式 `2025年5月10日`）解析出年月日 → **加上 `副本天数`** → 写回。
`现实时间`（`凌晨00:01`）**不动**。

### 5.8 周期（第十一步）

```
新周期 = 旧周期 + 1; if (新周期 > 10) 新周期 = 1
```

### 5.9 资格分累加（第十一步）

`契约者.资格分 += 本次资格分`（该字段即赛季累计）。

## 六、写变量的清单

| 路径 | 动作 | 值 |
|---|---|---|
| `头部.EXP_当前` | `+=` | 最终EXP |
| `经济.UP` | `+=` | 最终UP |
| `头部.RP_当前` | `+=` | RP |
| `职业.PEXP_当前` | `+=` | 最终PEXP |
| `资格分` | `+=` | 本次资格分 |
| `头部.CR` | `=` | 变动后（clamp 1~10） |
| `头部.回廊态度` | `=` | 按变动后 CR 查表 |
| `赛季信息.当前副本周期` | `=` | 5.8 的结果 |
| `当前时间.现实日期` | `=` | 5.7 的结果 |
| `副本经历.<副本名称>` | `=` | `{ 评价等级, 简要说明: 史诗记录 }` |
| `头部.称号.备用称号（只记录不生效）` | `=` | AI 给的称号（**仅 A/S 级**） |
| `小队.成员.<名>.头部.EXP_当前` | `+=` | **与玩家相同的**最终EXP |
| `小队.成员.<名>.背包['现金UP']` | `+=` | **与玩家相同的**最终UP |
| `背包.<掉落物名>` | `=` | `{ 描述, 数量, ...品质/属性/效果 }` |
| `其他契约者` / `副本角色` / `其他契约者名单` / `固有角色名单` | `=` | `{}` |
| `当前副本元数据` | `=` | 字段级清零（副本名称/来源/类型/时间限制→「未生成」，基准等级→1） |
| `当前副本任务` | `=` | 主线任务回默认；支线/世界事件/隐藏/成就 → `{}` |

**不写**：`称号.当前称号`（交给聊天）、`头部.EXP_升级所需`、`军衔`、`RP_下一级`、`职业.PEXP_升级所需`、`职业.职业等级`、`衍生属性.*`、`属性.*` —— 这些全由前端脚本代算。

## 七、错误处理

| 情况 | 行为 |
|---|---|
| `当前副本任务.主线任务.状态 === '失败'` | **不结算**。提示「主线失败 = 抹杀，不进入结算流程」，不发 AI 请求、不写任何变量 |
| 没有 `当前副本元数据.副本名称` 或为「未生成」 | 提示「当前没有进行中的副本」，不结算 |
| 奖励文本解析失败 | **明确报错**，指明是哪一条任务的 `奖励` 字段格式不对；不写任何变量 |
| AI 返回的 `完成的支线` 含变量里不存在的键名 | 忽略该项并在画面里以「（变量中未找到：X）」标明，不静默吞掉 |
| 写入回读校验失败 | 抛错 → `toastr.error('写入未生效: 字段名与存档 schema 不匹配 → 路径')`，与敌人生成同款 |
| 写入期间条目被切换/清空 | 与敌人生成同款：回填前校验，不可回填时如实告知 |

## 八、测试策略

`settlementRules.ts` 是纯函数，**全部算术与解析由单测覆盖**：

- 奖励文本解析（正常 / 缺 RP / 无物品段 / **格式非法时必须抛错**）
- 资格分各分项与合计
- 评价倍率 × CR倍率 × 位阶修正的乘算（含 D 级 ×0.7、炼狱 ×1500%）
- **CR 分档的 floor 边界**（2.0 / 2.5 / 3.0 / 9.9 / 10）
- RP 各来源（含成就按星数、S级+3、炼狱附加仅在 CR=10 时）
- PEXP
- CR 变动与 10→3 回调
- 周期 10+1=1
- 现实日期加天数（跨月、跨年）
- 面板拼装的每一行（含非 A/S 级时称号行留空）
- 写入清单的结构（**断言被禁字段一个都不出现**）

`settlementGen.ts` 的 prompt 由冒烟测试钉关键要素。

**不做**：store 与 UI 的自动化测试（够不到 `Mvu`/`toastr`），与敌人生成裁决一致。

## 九、已知取舍

1. **依赖奖励文本格式。** 变量里存的是文本而非结构化数值，模块只能解析。若游戏过程中 AI 改写了 `奖励` 文本，解析会失败 —— **设计上选择明确报错而不是当 0**，让问题可见。
2. **完成与否以 AI 报告为准**，不读变量 `状态` 字段。AI 漏报会导致少算奖励，玩家可在画面上看到逐项来源并「重算」。
3. **面板由模块拼**，所以 `## 掉落清单` 等自由文本内容来自 AI，但**所有数字来自模块**。
4. **不做结算后流程** —— 画面末尾列出两个选项，由聊天接手。
5. **CR 的 2.5/9.9 这类中间值取了 floor 分档**（待确认）。
6. **`## 职业进度` 与 `## 军衔状态` 是照抄现有字段**（`职业.PEXP_升级所需` / `头部.军衔`），模块不算 —— 它们由前端脚本维护。若前端没维护，会显示 0/旧值。

## 十、验证方式

代码侧：单测覆盖全部算术与解析。
**实机验收**（交付时给清单）：打一次副本 → 点结算 → 看画面数字是否符合预期（尤其倍率乘算）→ 点确认 → 读存档核对四个增量 / CR / 资格分 / 周期 / 现实日期 / 副本资料已清空 / 队友也拿到 EXP 与「现金UP」→ 再点一次结算应提示「没有进行中的副本」。
