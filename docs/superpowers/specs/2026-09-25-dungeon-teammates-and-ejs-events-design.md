# 副本生成 · 队友来源锚定 / EJS 动态事件注入 / 晋升试炼支线 · 设计

> 2026-09-25 与用户多轮对话确定，依据是当日在用户酒馆里跑的两次实测探针（见附录 A）。
> 规则原文见同目录的两份 `-verbatim` 文件（EJS 控制器、晋升试炼）。
> 本设计**只覆盖「副本生成」这一步**（`store.generate` / `buildDungeonPrompt`），
> **不含**敌人生成与副本结算 —— 那两步本次明确不动（用户 2026-09-25 拍板「只喂副本生成」）。
> 但 §七 记录了一条**必须一起做的跨模块改动**，否则本模块一上线就会让结算抛错。

## 一、目标

修掉副本生成现存的四个毛病：

1. **队友乱出。** 现在「其他契约者」在默认路径下**没有任何世界观约束** ——
   `buildMatchPool`（`store.ts:2293`）要么给一句「自由生成同阶契约者」，要么给一份回廊原生榜单，
   两者都不要求队友与本次副本的世界观有任何关系，AI 想出谁就出谁。
   规则原文（`data.ts:1040`）其实写了「IP角色须有被匹配可能（具体IP与角色由GM按核心特色标签1d50决定）」，
   但这条**从未落进 prompt**。

2. **动态事件不在生成视野里。** 玩家卡里有一套 EJS「主线事件控制器」条目，按
   赛季 / 周期 / 阶位 / 当前世界判定哪些 `事件_*` 条目本轮生效。它靠「提示词模板语法」插件
   在**正常酒馆生成**时生效，而小手机的 AI 通道是 `aiGenerate` → `generateRaw`
   （`ordered_prompts: ['user_input']`、`max_chat_history: 0`，见 `store.ts:353`），
   **完全绕开酒馆的提示词装配**，因此世界书与 EJS 一概不参与。
   于是「周期 3 该撞上白焰降临」「周期 5 是淘汰赛」这类事实，生成副本的 AI 根本不知道。

3. **事件应当有最高权威。** 淘汰赛、晋升试炼这类事件不是「背景参考」，
   它们**改写本次副本的规则本身** —— 副本类型、主线、支线都得跟着走。

4. **晋升试炼没人发。** 规则（`<晋升试炼>`）要求玩家满当前位阶上限时，
   下一次副本必须额外发一条专属晋升支线；现在完全没有这个机制。

### 一.1 本模块的边界（用户 2026-09-25 明确划定）

**副本生成只负责「确定副本资料」** —— 副本元数据、主线任务、支线任务、世界事件、副本成就、
固有角色名单、其他契约者名单。

动态事件里的以下内容**不属于本模块**，交给**正文 API**（聊天侧生成）处理：

| 内容 | 例子 |
|---|---|
| **数值锚定** | 白焰降临：「塞拉菲娜对{{user}}的基础好感度锚定为 20」 |
| **敌人构筑** | 恶魔旅团：5 名成员的属性分配 / 职业技能 / 底牌 / 战术阵型 |
| **剧情走向** | 事件里写「这是未发生的剧情，只是提供剧情走向」的那部分 |

设计含义：事件段写进 prompt 的目的是让**副本资料与事件自洽**
（名单里该有的人必须在、副本背景与任务要与之相称），
而**不是**让本模块去落地事件的数值、敌人或剧情。**这两件事本次都不做。**

## 三、优先级阶梯（本设计的核心）

这一节是整份设计的**权威**。实现与 prompt 文案都必须与它逐条对应。

**一条总则：事件只在它「实际点到」的地方有权威。** 事件没提到的世界观 / 队友 / 任务，
下面各级照常生效；**一旦点到，它压过下面全部** —— 而不是「开了事件开关，其他一切作废」。

**从高到低：**

| 优先级 | 来源 | 强度 | 备注 |
|---|---|---|---|
| **0** | **动态事件**（**仅当事件开关打开**） | **最高**。可强制覆盖**世界观、副本内容、主线任务、支线任务、副本类型**；**若点名了具体契约者，则「其他契约者」完全由事件接管** —— 不再加同人契约者、不抽榜单，人数以事件写明的为准 | **本次新增**。见 §五 |
| 1 | 手填**「队友人物」**（自选模式） | 绝对 —— 必须恰好是他们，不多不少 | 现有 `队友锚定` 段。**事件未点到队友时**由它说了算 |
| 2 | 手填**「队友世界观」**（自选模式） | 强制来源世界观 | 同上 |
| 3 | **「同人契约者」开关**（CR≥5） | 开 → 恰好 1 名同人契约者 | **本次新增** |
| 4 | **队友标签 → IP 范围 → 世界观（≠副本世界观）→ 真人角色 + 性别** | 约束 IP 队友 | **本次新增** |
| 5 | **榜单匹配池**（CR≥5） | 回廊原生契约者的候选名单 | 现有，**一行不动** |
| 6 | AI 自由生成（CR≤4 的兜底） | 最弱 | 现有 |

**三条必须写进 prompt 的题外话：**

- **事件与手填指定冲突时，事件赢**（用户 2026-09-25 拍板），但界面必须**明确警告**
  是哪几项被事件覆盖了 —— 照本项目「宁可难看也不圆上」的一贯口径，不静默吞掉。
- **点名即接管队友**（用户 2026-09-25 拍板）：只要事件点名了具体契约者，
  「其他契约者」就**完全由事件决定** —— 不再加同人契约者、不抽榜单、不自由生成。
  人数以事件写明的为准（`事件_白焰降临` 明写「整个副本**仅有**他们三名契约者」⇒ 恰好 3 名，
  即 {{user}} + 塞拉菲娜 + 弗尔弗尔）。事件只点了名、没写人数时，就以点名的人为准，不再额外添人。
- **多个事件互相矛盾时不做裁决，原样喂给 AI**（用户 2026-09-25 拍板）。
  已知案例：副本 / 一阶 / 周期 3 会同时注入 `事件_恶魔旅团` 与 `事件_白焰降临`，
  两者对「弗尔弗尔怎么死」（用户反杀 vs 塞拉菲娜轰杀）与「副本里有几名契约者」说法不一致。
  模块**不做冲突检测、不在界面报警**，由 AI 自行圆场。**用户已知悉并接受。**
- **事件开关关闭时，第 0 级整级不存在** —— 连控制器都不渲染，其余各级回到原样，
  即关掉开关的玩家回到本次改动之前的旧行为。
  ⚠️ **但开关默认是开的**（用户 2026-09-25 拍板），所以对多数玩家而言本次属**行为变更**：
  §三.1 那句「以动态事件为准」的例外会**默认存在**，骰值不再是唯一权威。
  想要旧行为，把这个开关关掉即可。

### 三.1 与「锁定骰值」的冲突及其解法

现有 prompt 里有一段措辞极硬的话（`dungeonGen.ts:72`）：

> 「以下骰值由系统用密码学随机数掷定，已经锁定。你**严禁**改动、重掷、忽略、四舍五入或自行编造任何数值。」

事件要能强制覆盖**副本类型**（例如淘汰赛），就必须让这条**有条件让路**。解法：

- 平时照旧（保证骰值权威，这是整个模块的地基）；
- **仅当动态事件段存在**时，在锁定骰值段末尾追加一句：
  > 例外：若下文「本次副本的动态事件」强制要求某个字段（如副本类型），**以动态事件为准**，
  > 其余未被事件点到的骰值仍然严禁改动。
- 这句话**只在事件段存在时拼接**，避免给不开事件的玩家引入任何松动。

## 五、B · EJS 动态事件注入 · 设计

### 5.1 新文件 `src/wxhl-003/dungeonEvents.ts`

**纯函数，零酒馆依赖** —— `evalTemplate` / `prepareContext` **以参数注入**
（照 `settlementRules.ts` 注入 `掷` 的先例），这样不装插件也能单测。

```ts
export interface EventSection {
  段落: string;          // 要拼进 prompt 的正文；空串 = 不注入
  触发: string[];        // 本次判发生效的 事件_* 条目名（去重、保序）
  缺失: string[];        // 控制器引用了、但条目表里找不到的名字
  跳过原因?: string;     // 非空 = 整节被跳过，附原因（供界面提示）
}

export function findControllers(条目表): { 名称: string; 正文: string }[];
export function buildEventSection(args: {
  条目表: { 名称: string; 正文: string }[];
  evalTemplate: (code: string, ctx: Record<string, unknown>) => Promise<string>;
  prepareContext: () => Promise<Record<string, unknown>>;
  超时毫秒?: number;   // 默认 5000
}): Promise<EventSection>;
```

**控制器识别**：名字以 `EJS/` 开头 **或** 正文同时含 `<%` 与 `getwi(` —— **取并集**。
（用户卡上实测只有 1 条，两种判据都命中它。并集是为了以后加了第二条控制器也不会漏。）

**渲染**：
1. `ctx = await prepareContext()`
2. `shim = async (名) => { 记录 名; return 条目表.get(名) ?? '' }`
   —— 取不到时**既返回空串也记进 `缺失`**，绝不静默。
3. `await evalTemplate(控制器正文, { ...ctx, currentWorld: '副本', getwi: shim })`
   —— `currentWorld` 覆盖之所以有效，是因为控制器第一行是
   `if (typeof currentWorld === 'undefined') var currentWorld = getvar(...)`（实测已验证）。
4. **5 秒超时**（`Promise.race`），超时 → 整节跳过。

**产出**：`fired` 里筛 `事件_` 前缀、去重保序 → 取这些条目的正文 → 拼段落。

### 5.2 `dungeonGen.ts`

`buildDungeonPrompt` 新增可选参数 `动态事件段: string`，
插在**「回廊难度评估」之后、「契约者数据」之前**（即**在**「匹配参考」**之前**，与 §三 的优先级一致）。

段落正文（含三句硬话，缺一不可）：

```
============ 本次副本的动态事件（回廊已判定生效 · 最高优先级） ============
以下事件由回廊的事件控制器按你当前的赛季 / 周期 / 阶位 / 所处世界判定为【本次副本生效】。
它们不是建议，是本次副本**必然牵涉**的剧情；主线任务、世界事件、支线任务必须与之相称。

<逐条：事件名 + 正文>

【三条死命令】
1. 这些事件的优先级**高于上文所有锁定骰值与自选指定**。若某个事件强制要求某个字段
   （副本类型、世界观、主线任务、支线任务、副本内容），**以事件为准**，不要因为与骰值冲突就改掉事件。
2. 上面**未列出**的动态事件，本次【一律不生效】—— 严禁把它们的剧情、人物、势力写进副本。
3. 上面**已列出**的事件若点名了具体契约者，**「其他契约者」完全由事件接管**：
   点名的人必须**全部在场、不多不少**；此时**不要**再从后文「匹配参考」抽榜单，
   也**不要**再加同人契约者。事件写明了人数就以它为准
   （如「整个副本仅有他们三名契约者」⇒ 恰好 3 名）。
```

> ⚠️ **刻意不加的一条**：多条事件互相矛盾时**不写任何裁决条款**（用户 2026-09-25 拍板
> 「不裁决，交给 AI」）。事件正文自带「这是未发生的剧情……但是节点必定发生」的措辞，
> 由 AI 自行圆场。**后来者不要"好心"补一条「以更具体者为准」之类的规则** —— 那会推翻这个决定。

- `dungeonGen.generate()`：**先判事件开关** —— 关闭时**连 `buildEventSection` 都不调**；
  打开时调它，段落传进 prompt。`跳过原因` 非空时写 `lastError`，
  提示「本次未注入动态事件：<原因>」，**但生成照常进行**。

### 5.3.1 点名软校验（新增 AI 输出字段）

「事件点名了谁」不能靠正则从散文里抠（事件正文是自然语言，抠不准）。改为**让 AI 自己报**：

- `DungeonGenResultSchema` 新增一个**可选**字段：
  ```ts
  事件点名角色: z.array(z.string()).prefault([]),
  ```
  prompt 里要求 AI 把「本次生效事件**强制要求在场**的人物」逐个列进去（真名，逐字）。
  加 `.prefault([])` ⇒ 老路径（不开事件）没有任何影响，AI 不回这个字段也不报错。
- **软校验**：拿这个名单去比对 `其他契约者` 与 `固有角色` 的名单（两边都找），
  缺谁就写 `lastError` 提示「事件点名的人物未出现在名单里：<缺失名单>」。
  **只报警、不阻断** —— AI 的输出仍是最终结果，照本项目「宁可难看也不圆上」的一贯口径。
- **为什么让 AI 报而不是我们解析**：解析散文名字必然漏（`{{user}}`、称号、全名/简称混用），
  而 AI 已经读过事件全文，让它复述是零成本的。代价是多一个字段、多一次「AI 可能不回」的容忍分支。

### 5.4 事件开关（`App.vue` + `store.ts`）

- 掷骰面板新增**「读取动态事件」复选框**，**每轮单独选**（随 `RolledDungeon` 持久化，同 §4.3）。
- 与自选字段的冲突：见 §三 第 1 条题外话 —— **事件赢 + 明确警告**。
  警告文案要**点名**被覆盖的字段（如「本次事件强制副本类型为【血腥】，已覆盖你的自选【和平】」）。
  实现上不做事后比对（那要求解析 AI 输出），而是**在事件段存在时直接给出通用警告**：
  「已开启动态事件：其优先级高于下方所有自选字段，冲突时以事件为准」。
- `RolledDungeon` 新增 `事件开关: boolean`。

### 5.5 前端展示

- 生成结果卡片里，把**本次生效的事件名**列出来（`EventSection.触发`），
  让玩家一眼看到「这轮撞上了什么」。放在副本名称下方，不额外占大块版面。

## 六、C · 晋升试炼支线 · 设计

规则原文见 `2026-09-25-ascension-trial-verbatim.md`。

### 6.1 触发判定

```ts
/** 阶位上限（硬编码，用户 2026-09-25 拍板）—— 五阶不在表内，故 Lv.100 不触发 */
const 阶位上限 = [20, 40, 60, 80];   // 下标 = 归一位阶(阶位) 的返回值 0..3
```

- `idx = 归一位阶(阶位)`；`idx !== undefined && idx <= 3 && 等级 >= 阶位上限[idx]` → **触发**。
- 用 `>=` 而非 `==`：AI 或结算多给经验时不至于漏判。
- 五阶（`idx === 4`）与认不出的阶位 → **不触发**。

**放在哪**：`PlayerBrief` 新增 `晋升试炼: boolean`，由 `readPlayerBrief()` 算好
（照 `PlayerBrief` 现有四字段的做法 —— 它是「从存档摘出来的玩家简报」，判定属于同一层）。

### 6.2 `dungeonGen.ts`

触发时追加一段（位置：紧接「本副本类型 / 时间限制」之后，**在**动态事件段**之前** ——
晋升试炼是骰值之外的系统强制项，但事件仍可以再覆盖它）：

```
============ 晋升试炼（回廊强制 · 不可拒绝） ============
契约者已达到当前位阶上限（Lv.<等级>），回廊强制触发晋升试炼。
- 你生成的**第 3 条支线任务**必须就是【专属晋升任务】，且**恰好是第 3 条**（不改条数）。
- 它的难度必须是**极高**：单杀隐藏BOSS / 收集特定规则道具 / 完成某某仪式 一类，
  不是普通支线能比的；说明里要写清判定方式。
- 它的「物品名」字段填空字符串（本次不给物品奖励）。
- 它的**奖励由系统另行写入**（晋升奖励），你**不要**输出 UP / EXP / RP 相关文字。
- 若本次同时生效了「回廊淘汰赛」等事件：晋升任务仍以支线形式发放，
  **不干涉淘汰赛的生存与排名规则**；队伍中其他未晋升的队友可协助完成它。
- 主线与晋升支线的关系：主线成功但晋升支线未完成 = 晋升失败（**无惩罚**）；主线失败 = 抹杀。
```

### 6.3 `dungeonRules.ts`

`mapToVariables` 需要知道是否满级，才能把第 3 条支线的 `奖励` 换成晋升奖励。
`mapToVariables(result, build, rewards, player)` 已有 `player`，故直接读 `player.晋升试炼`：

```ts
/** 晋升奖励原文（逐字照 <晋升试炼> 文档） */
const 晋升奖励表 = [
  '一阶→二阶: 等级上限+20，+3自由属性点，天赋品质强制提升1级。',
  '二阶→三阶: 等级上限+20，+5自由属性点，天赋品质强制提升1级。',
  '三阶→四阶: 等级上限+20，+5自由属性点，天赋品质强制提升1级。',
  '四阶→五阶: 等级上限+20，+8自由属性点，天赋进入完全体形态。',
];
/** 奖励字段的固定前缀 —— 结算侧的 parseRewardText 靠它识别「非数值奖励」（见 §七） */
export const 晋升奖励前缀 = '【晋升试炼】';
```

- 触发时：`支线任务[第3条.名称].奖励 = 晋升奖励前缀 + 晋升奖励表[idx]`
- **不**调 `composeRewardText`（那条路径产出的是 `N UP + N EXP` 数值文本，见 §七）。
- 第 3 条的 `物品名` 来自 AI，触发时忽略（AI 被要求填空串）。

### 6.4 已知的取舍：第 3 组支线骰空转

`rollRewards`（`dice.ts:585`）固定掷 **3 组**支线奖励。满级时第 3 组**不被使用**，
但**掷骰明细里照样显示**。

- **为什么不改 `rollRewards`**：它只收 `() => { rewards, records }`，拿不到玩家等级；
  要传等级就得改它的签名与全部调用点，而收益仅仅是「明细里少一行」。
- **代价**：玩家可能看到明细里第 3 组支线骰，却发现生成的支线奖励不是它。
- **缓解**：触发晋升试炼时，在掷骰明细的第 3 组支线行后加一句小字
  「本次为晋升试炼，第 3 条支线的奖励由系统指定」。
- 用户 2026-09-25 已知悉并接受（决定 #20）。

### 6.5 不改的东西

- `App.vue:1630` 的「支线任务 ×3」**保持写死** —— 条数确实仍是 3，契约未破。
- `statusbar` 无需改动（按 record 遍历，多少条都渲染）。
- **楼内正则版**（不在本仓库）不受影响 —— 条数没变，这是选「替换第 3 条」而非「开第 4 条」的主要理由。

## 七、跨模块接口契约：生成 → 结算（**阻塞项**）

⚠️ **本节是本次唯一的跨模块改动。不做的话，本模块一上线，玩家一旦完成晋升支线，结算必然抛错。**

### 7.1 问题

`settlementRules.ts:16` 的 `parseRewardText` 是**严格格式**的，只认
`N UP + N EXP (+ N RP) (+ 【类型】名：描述)`；**格式不符直接抛错**，注释写明「绝不静默当 0」。

而 `汇总基础奖励`（`settlementRules.ts:344`）会把 AI 报告**已完成**的任务名拿去解析 `奖励` 文本。
晋升支线的 `奖励` 是 `【晋升试炼】一阶→二阶: 等级上限+20，…` —— **不是那个格式**。

⇒ 玩家完成晋升支线 → AI 报进 `完成的支线` → `parseRewardText` 抛错 → **整次结算被挡**。

### 7.2 改法（最小）

`settlementRules.ts` 的 `parseRewardText` 增加一条**合法的非数值奖励形态**：

- 文本以 `晋升奖励前缀`（`【晋升试炼】`）开头 → 返回 `{ UP: 0, EXP: 0, RP: 0 }`；
- **其余行为一字不改**（非法格式仍抛错，静默当 0 的做法仍然禁止）。

配套：`晋升奖励前缀` 常量由 `dungeonRules.ts` 导出，`settlementRules.ts` 从那里 import ——
**单一来源**，避免两处各写一份字符串而漂移（照本项目对「重复文案」的一贯态度）。

### 7.3 后果与验证

- 完成晋升支线：`汇总基础奖励` 给它记 0 UP / 0 EXP（**符合规则「没有更多的其他奖励」**），
  资格分的「支线 +5/条」照给（它数的是 `完成的支线.length`，与奖励文本无关）。
- 测试：`settlementRules.test.ts` 补「晋升奖励前缀 → 零奖励、不抛错」；
  另补一条「前缀相同但后面乱写 → 仍返回零奖励」（前缀即契约，不解析后缀）。

### 7.4 顺带记录（**本次不修**）

- `data.ts:1467` 的 CR 变动表写着 `晋升通过+1.0 | 晋升失败-1.0`，
  而 `settlementRules.ts:224` 的 `CR变动表` **只有 S/A/B/C/D/F**。晋升在结算侧整体缺失。
- `settlementRules.ts:140` 的 `阶数()` 遇到 `超脱者` 会抛错（见附录 A.1 第 3 条）。

两条都属结算模块，**等用户细说结算时一并处理**。

## 八、降级与失败策略

**任意一条成立 → 整节跳过 + 界面提示 + 生成照常：**

| 情况 | 跳过原因文案 |
|---|---|
| 事件开关**未打开** | （不提示 —— 这是玩家自己的选择） |
| `typeof EjsTemplate === 'undefined'` | 未安装「提示词模板语法」插件 |
| 找不到任何控制器条目 | 世界书里没有 EJS 控制器条目 |
| `prepareContext()` 抛错 | 插件环境初始化失败：`<错误>` |
| `evalTemplate` 抛错 | 控制器渲染失败：`<错误>` |
| 超过 5 秒 | 控制器渲染超时 |
| 渲染成功但没触发任何 `事件_*` | **不算失败** —— 正常不注入（例如周期 1 本来就没有事件） |

`缺失` 非空时**不跳过**，但在界面上如实列出「控制器引用了但找不到的条目」——
照本项目一贯口径，宁可难看也不圆上。

### 八.1 为什么把控制器里的 4 条规则条目一并丢弃

控制器在 `currentWorld === '副本'` 时还会 `getwi` 四条规则条目。本设计**只取 `事件_*`**，
规则条目**丢弃**。理由：

- 其中 `<副本角色生成规则>` 仓库里已内联为 `ENEMY_GEN_RULES`；
- 但另三条（`副本任务规范` / `敌人模板设计` / `副本任务变种`）**仓库里没有**；
- 且世界书里的 `敌人模板设计`（**模板**）与仓库内联的 `<敌人模版设计>`（**模版**）**用字不同**，
  两条一起喂会给 AI 互相矛盾的规则。

所以本次**只做事件**，规则条目留到专项处理（用户 2026-09-25 拍板「先只喂事件」）。
**但代码里会保留一行注释点名这个事实**，免得以后有人以为「控制器只吐事件」。

```js
(async () => {
  const E = window.EjsTemplate, T = window.TavernHelper ?? window;
  const ctx = await E.prepareContext();
  const wb = T.getCharWorldbookNames('current').primary;
  const es = await T.getWorldbook(wb);
  const ctrl = es.find(e => (e.content || '').includes('getwi(') && (e.content || '').includes('currentCycle'));
  const byName = new Map(es.map(e => [e.name, e.content || '']));
  const fired = [];
  const rec = async n => { fired.push(n); return byName.get(n) ?? ''; };
  for (const w of ['副本', '回廊', '现实'])
    for (const r of ['一阶', '二阶', '三阶', '四阶', '五阶', '超脱者'])
      for (let c = 1; c <= 10; c++) {
        fired.length = 0;
        try { await E.evalTemplate(ctrl.content, { ...ctx, currentWorld: w, currentRank: r, currentCycle: c, currentSeason: 21, getwi: rec }); } catch (_) { continue; }
        const f = [...new Set(fired)].filter(n => n.startsWith('事件_'));
        if (f.length) console.log(w + ' / ' + r + ' / 周期' + c + ' → ' + f.join(', '));
      }
})();
```

### 附录 A.1 · 顺带发现（本设计不处理，但已记录）

1. **`事件_医者仁心` 永远不会被触发。** 它是 18 个 `事件_` 条目之一，
   但全卡**唯一**的 EJS 条目（`EJS/主线事件控制器`）一次都没 `getwi` 它，
   且 18 个事件条目**本身都不含 EJS**（`ejsEntries` 只有 1 条即证据）。
   除非它是绿灯条目（靠关键词扫描），否则这条内容永远不会进 prompt。
   **待用户确认是有意为之还是漏写。**

2. **`当前赛季` 的默认值两处不一致。** 控制器用 `getvar(..., { defaults: 0 })`，
   状态栏（`statusbar/core.ts:1933`）用 `d('契约者.赛季信息.当前赛季', 21)`。
   实测存档里该字段**确实是 21**，所以当前不出问题；但一旦该字段丢失，
   状态栏会显示 21 而控制器拿到 0，**6 个依赖赛季 21 的事件会静默哑火**。

3. **`超脱者` 阶位会让结算直接抛错。** 控制器第 83 行按 `currentRank === '超脱者'` 判断，
   而 `settlementRules.ts:140` 的 `阶数()` 走 `归一位阶`，**只认一~五阶**，
   遇到 `超脱者` 会抛 `阶位无法识别, 不能结算`，把整次结算挡下。
   属副本结算模块的问题，**另行处理**。

4. **规则条目在仓库与世界书之间有漂移。** 控制器 `getwi('敌人模板设计')`（**模板**）
   与 `data.ts:1289` 的 `<敌人模版设计>`（**模版**）用字不同；
   另 `副本任务规范` / `副本任务变种` 两条仓库里**根本没有**。

5. **`data.ts:1467` 的 CR 晋升项在结算里缺失**（详见 §7.4）。

6. **周期 3 的两条事件互相矛盾**（用户已知悉并接受，**不裁决** —— 见 §三）：
   - `事件_恶魔旅团`：「{{user}}在第三次副本内遭遇…弗尔弗尔…**经历苦战后被契约者反杀**」
   - `事件_白焰降临`：「塞拉菲娜…对弗尔弗尔展开了绝对的过度杀伤：**弗尔弗尔的尸体在白火中彻底消失**」
   同一人、同一周期、两种死法；两边对「副本里有几名契约者」的说法也对不上
   （恶魔旅团读起来是用户单独遭遇，白焰降临明写「仅有他们三名契约者」）。
   矩阵实测这两条在 **副本 / 一阶 / 周期 3** 会**同时注入**。

## 十二、实现补记（2026-09-25 收尾）

> 正文描述的是**设计意图**，本节描述的是**实际落地**；两者冲突时以**代码**为准。

### 12.1 接口落地方式与正文不同

1. **`buildDungeonPrompt` 只加了一个可选分组参数，不是正文 §九 的四个。**
   正文 §九 写的是「新增参数：`队友标签`、`同人契约者`、`动态事件段`、`晋升试炼段`」；
   实际签名末尾只多了一个分组对象（`dungeonGen.ts:43-54`）：

   ```ts
   附加?: {
     同人契约者?: { 开关: boolean; 性别: string };
     动态事件段?: string;
     晋升试炼?: boolean;
   }
   ```

   原因：该函数此前已有 10 个位置参数（`dungeonGen.ts:32-42`），散着加会到 13 个。
   **`队友标签` 不进参数** —— 它从 `build.队友标签` 读（`dungeonGen.ts:88`、`:91`），
   因为 `build` 本来就是第 1 个位置参数。

2. **`晋升奖励前缀` 常量落在 `dice.ts`，不是正文 §七.2 写的 `dungeonRules.ts`。**
   正文 §七.2 写「由 `dungeonRules.ts` 导出，`settlementRules.ts` 从那里 import」；
   实际常量定义在 `dice.ts:653`，`settlementRules.ts:1` 与 `dungeonRules.ts:2`
   都从 `'./dice'` import 它（§九 清单同样写作 `dungeonRules.ts` 导出，一并以此为准更正）。
   原因：它是「奖励文本格式」的一半，另一半 `composeRewardText` 就在同一文件（`dice.ts:656`）；
   且这样 `settlementRules.ts` 不必反向依赖 `dungeonRules.ts`
   ——**单一来源**这个要求仍然成立，只是换了个文件。

3. **`事件点名角色` 的输出契约是补进 `dungeonGen.ts` 的（正文 §5.3.1 漏了生产端）。**
   正文 §5.3.1 只定义了 schema 字段（`.prefault([])`）与软校验，**没写谁告诉 AI 去填它** ——
   不补的话该字段恒为 `[]`，软校验就成了死代码。落地时补进了输出 JSON 契约
   （字段在 `dungeonGen.ts:221`）与一段说明（`dungeonGen.ts:233-235`）：

   > 「事件点名角色」只填**本次生效的动态事件强制要求在场**的人物**真名**（逐字，与事件正文一致）。
   > **绝对不要把契约者本人（{{user}}）列进去** —— 他必然在场，写进去会被系统判成「点名了缺席者」。

   配套测试在 `dungeonGen.test.ts:184-191`。**后来者不要把这段契约当成多余的话删掉** ——
   删了它就退回死代码。

### 12.2 实现期间对正文的**有意偏离**（勿按正文改回）

1. **晋升试炼段的插入位置与正文 §六.2 的字面锚点不同。**
   正文写「紧接『本副本类型 / 时间限制』之后」；实际插在「回廊难度评估」之后、
   **紧贴动态事件段之前**（`dungeonGen.ts:195`：`${晋升试炼段}${动态事件段 ? … }`）。
   理由：prompt 里并没有一个叫「本副本类型 / 时间限制」的段名；且新位置在语义上更好
   ——与它要压制的动态事件段相邻。

   > ⚠️ **更正一处转述**：实现台账的最终评审 Ruling 称「测试钉住了新位置」，**实测不成立**。
   > `dungeonGen.test.ts` 里唯一钉位置的是**动态事件段**（`:154-155` 断言
   > 「回廊难度评估」< 事件段正文 < 「契约者数据」）；`晋升试炼段` 的两条用例
   > （`:170-182`）只断言**内容存在**，**没有任何位置断言**。
   > 即新位置目前**只由实现保证、无测试守护**——若将来有人按正文 §六.2 把它挪走，测试不会红。

2. **晋升试炼段省略了 `（Lv.<等级>）`。**

### 12.3 正文未覆盖、实现期间新增的行为

1. **「队友来源锚定」段是条件注入的。**
   正文 §4.2 把这段当成必然出现；实际只有当 `build.队友标签` 为真值时才拼（`dungeonGen.ts:88`）。
   原因（`dungeonGen.ts:83-87` 的注释）：`队友标签` 是本分支新增的**必填**字段，
   而条目来自 `loadRolledDungeons()` 的 `localStorage` + `JSON.parse`（`store.ts:2332-2334`，**无迁移**）
   ——base 版本掷出的旧条目根本没有这个键，类型上的必填拦不住运行时。
   此时**整段不出现**（不退化成「= undefined」的假段落），
   照「宁可难看也不圆上」的口径诚实降级。

2. **`reroll()` 现在也接收两个开关并原样透传。**
   正文完全没提 `reroll`。原先它无参调 `doRoll()`，会把玩家勾的开关**静默重置**
   （同人开关 → `false`）。现在签名与 `doRoll` 逐字同款并透传（`store.ts:2692-2699`），
   调用点带上当前面板值（`App.vue:2629`）。

3. **面板开关会随条目回填（正文只写了「每轮单独选」）。**
   `eventEnabled` / `mateEnabled` / `mateGender` 会从当前条目的
   `事件开关` / `同人开关` / `同人性别` 单向同步（`App.vue:2549-2555`），
   触发点是**选中历史条目**（`watch` 条目 id，`App.vue:2557`）与**进入面板**（`App.vue:2475`）。
   目的：避免面板显示与这一轮实际行为不符的勾选——最坏是一条误导性警告
   （面板写着「事件优先」，而这一轮根本不注入事件）。

4. **超时预算是「两段各一份」，最坏约 10 秒（正文 §八 只写「超过 5 秒」）。**
   实际 `prepareContext()` 与 `evalTemplate` **各**套一份 5 秒预算
   （`dungeonEvents.ts:131` 的 `超时` 常量被 `:138` 与 `:144-153` 两处 `带超时` 复用），
   因此最坏约 10 秒才降级。理由：§5.1 的「5 秒」原文写在**第 4 步**（`evalTemplate` 那一步），
   当时还没有 `prepareContext`；给两段各自一个预算比共享 deadline 更好
   ——慢一点的插件初始化不该把渲染预算吃光、导致连尝试都不尝试。
   代价：最坏 5s → 10s，但仍然有界，且两种情况下玩家看到的都是「生成中...」。
   另：超时有**自己的文案**（`dungeonEvents.ts:95-96`），不会被 `catch` 前缀污染成
   「控制器渲染失败: 控制器渲染超时」——这正是 §八 表里那两行文案字面要求的样子。
